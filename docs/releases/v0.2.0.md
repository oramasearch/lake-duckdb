# lake-duckdb v0.2.0

The first tagged release of lake-duckdb, powered by DuckDB: one DuckDB database behind a small HTTP
API with a bearer token, the web service behind lake's DuckDB services. It is cut from `dev` at
`ff49b0e` and carries the open-source launch work of epic
[#1](https://github.com/oramasearch/lake-duckdb/issues/1). Tracking issue:
[#16](https://github.com/oramasearch/lake-duckdb/issues/16). This release was not planned through a
release epic, so these notes list what merged.

An image tagged `0.1.0` was published earlier without a Git tag or release notes. This release is
the first with both. It changes behavior (see *Changes since 0.1.0*), so it is a minor version.

## What it includes

### The service

- **One binary** (`cmd/lake-duckdb`) serving one DuckDB database file over HTTP, built with
  `github.com/duckdb/duckdb-go/v2` v2.10505.0, which links DuckDB **v1.5.5** statically through cgo.
  The loaded extensions are `core_functions`, `parquet`, `json`, `icu` and `autocomplete`.
  `lake-duckdb --version` prints the version, and the startup log carries it.
- **Configuration** from the environment ([`docs/api.md`](../api.md#configuration)):
  `LAKE_DUCKDB_TOKEN` (required), `LAKE_DUCKDB_PATH` (default `/data/main.duckdb`),
  `LAKE_DUCKDB_ADDR` (default `:8080`), `LAKE_DUCKDB_MEMORY_LIMIT` (DuckDB gets half the container
  limit, the Go heap a quarter) and `LAKE_DUCKDB_THREADS`.
- **Routes** ([`docs/api.md`](../api.md#api)):
  - `POST /v1/query`: `{sql, params}` answers `{columns, rows}`. It returns at most 10,000 rows and
    32 MiB of values, and sets `truncated` when it cuts.
  - `POST /v1/exec`: answers `{rows_affected, last_insert_id}`. `last_insert_id` is always `null`,
    because DuckDB has no rowid.
  - `POST /v1/batch`: runs its statements in order, in one transaction. The first error rolls the
    whole batch back. A statement that returns data answers like `/v1/query`, any other like
    `/v1/exec`.
  - `GET /healthz`: needs no token. It answers 200 while the database answers `SELECT 1` within two
    seconds, on a connection kept for it.
- **Auth:** `Authorization: Bearer <token>` on every route but `/healthz`, compared in constant
  time on SHA-256 hashes. A bad or missing token gets 401 before the route or method is looked at.
- **Values:** every DuckDB type maps to JSON. `DECIMAL` is an exact string, `HUGEINT` an exact
  integer, `BLOB` `{"$base64": ...}`; dates, times, timestamps, intervals, `LIST`, `ARRAY`,
  `STRUCT`, `MAP` and `UNION` are covered too
  ([the table](../api.md#values-in-answers)). Parameters bind as `BIGINT`, `DOUBLE`, `VARCHAR`,
  `BOOLEAN`, `NULL` or `BLOB`.
- **Bounds:**
  - request bodies up to 16 MiB;
  - 30 s per request, after which the statement is interrupted;
  - four API connections at a time, plus one for `/healthz`;
  - headers read within 10 s, and idle connections closed after 2 minutes.
- **Errors:** every error has one shape, `{"error": {"code", "message"}}`, with these codes:
  `sql_error`, `invalid_request`, `invalid_params`, `unauthorized`, `forbidden`, `not_found`,
  `method_not_allowed`, `conflict`, `body_too_large`, `io_error`, `internal`, `out_of_memory`,
  `unavailable`, `timeout` and `disk_full`.
- **Lifecycle:** on `SIGTERM` or `SIGINT`, in-flight requests get 30 s to finish, then the database
  closes, which checkpoints the WAL.
- **Logging:** one JSON line per request (method, path, status, sizes, duration). The SQL, its
  parameters, the body, headers and the token are never logged.

### The lockdown and the statement guard

The lockdown and the statement guard are described in [`docs/api.md`](../api.md#the-lockdown).

- **The engine is locked before the service answers.** No file access beyond its own database, and
  no network (`enable_external_access=false`). No extension install, autoload or community
  extension. Memory and thread limits apply, and then `lock_configuration=true`. The service checks
  the lock on two connections and exits rather than serve an unlocked engine.
- **One statement per `sql`.** DuckDB's own parser counts the statements before anything runs. More
  than one answers `400 invalid_request`.
- **Refused statement types, with `403 forbidden`:** `COPY`, `EXPORT DATABASE` and `DETACH`.
- **Functions and pragmas that change state past the lock.** These are refused with `403 forbidden`
  wherever they appear in a statement: logging, profiling, progress bars, verification modes,
  optimizer, object cache, checkpoint-on-shutdown and the PEG parser switches,
  `json_execute_serialized_sql`, `arrow_scan`, and any call of `query(...)`. The tests classify
  every PRAGMA and table function of DuckDB v1.5.5.
- **A fresh connection for every request**, closed when the request ends. No transaction or
  connection setting outlives its request.
- **DuckDB's stdout is detached** from the request log.

### The image

`oramasearch/lake-duckdb:0.2.0` (also `v0.2.0`, with the same digest), `linux/amd64`. It is built
by the [`Dockerfile`](../../Dockerfile):

- the builder is `golang:1.27.4-bookworm`, and the runtime is
  `gcr.io/distroless/cc-debian12:nonroot` (glibc, no shell), both pinned by digest;
- it runs as user `65532:65532`;
- libstdc++ and libgcc are linked statically;
- an empty `/data` is owned by the runtime user.

## Changes since 0.1.0

- **Security fixes** from the pre-release review, each with its tests:
  - [#7](https://github.com/oramasearch/lake-duckdb/issues/7) (high): `COPY ... TO` could overwrite
    the database file or its WAL.
  - [#8](https://github.com/oramasearch/lake-duckdb/issues/8) (high): `enable_logging` wrote
    customer SQL and data to the pod's log.
  - [#9](https://github.com/oramasearch/lake-duckdb/issues/9): the Go 1.25 builder.
  - [#10](https://github.com/oramasearch/lake-duckdb/issues/10): logging to a file wedged and
    aborted the engine.
  - [#11](https://github.com/oramasearch/lake-duckdb/issues/11): profiling and similar pragmas got
    past the lock.
  - [#12](https://github.com/oramasearch/lake-duckdb/issues/12): answers had no byte bound.
  - [#13](https://github.com/oramasearch/lake-duckdb/issues/13): connection state outlived its
    request, and `DETACH`.
  - [#14](https://github.com/oramasearch/lake-duckdb/issues/14): a multi-statement `sql` committed a
    batch half-way.
- **New refusals:**
  - A `sql` with several statements: `400 invalid_request`. Send them through `/v1/batch`.
  - `COPY`, `EXPORT DATABASE`, `DETACH`, and the functions above: `403 forbidden`.
- **Answers stop at 32 MiB of values** (counted as JSON writes them, and shared by a batch), marked
  `truncated`.
- **The builder moves** from Go 1.25 (out of support, 9 reachable standard-library advisories) to
  Go 1.27.4.
- **The Dockerfile** builds on any architecture natively, and ships `/data` owned by the runtime
  user.

## What it does not include

- Replication, backups or a second copy of the database
  ([orama-operator#453](https://github.com/oramasearch/orama-operator/issues/453)).
- Reading files or URLs: data arrives through `INSERT`, and `COPY` is refused.
- TLS: it serves plain HTTP, for use behind TLS or inside the cluster.
- A signed image, an image SBOM attestation, or a public image
  ([#17](https://github.com/oramasearch/lake-duckdb/issues/17)). The repository SBOM covers the
  source tree.

## Known issues

Security first:

- [#15](https://github.com/oramasearch/lake-duckdb/issues/15) (info, accepted): DuckDB's error
  messages name paths inside the pod, and the API is plain HTTP.
- The statement guard is a list of names for DuckDB v1.5.5. It stands in for the upstream fix of
  [duckdb#28110](https://github.com/duckdb/duckdb/issues/28110). It also refuses a refused name
  inside a string literal.
- [#18](https://github.com/oramasearch/lake-duckdb/issues/18): the final pre-launch review of the
  published commit is still owed. This release's review had two independent reviewers, but both
  ran on the same model.

Others:

- [#5](https://github.com/oramasearch/lake-duckdb/issues/5) (release blocker for the open-source
  launch): the image still carries glibc (LGPL) from its distroless base, and statically linked
  libstdc++ and libgcc (GPL with the runtime exception). A `FROM scratch` image with DuckDB built
  from source on musl and libc++ is in progress.
- The TPC-H and TPC-DS extensions are linked into the binary but not loaded, and `LOAD tpch` is
  refused. Their code is under the TPC End User License Agreement, which is not an open-source
  license, and legal review is pending
  ([orama-bridge#276](https://github.com/oramasearch/orama-bridge/issues/276)).
- One pod on one volume: a lost volume loses the database.
- [zetta#1382](https://github.com/oramasearch/zetta/issues/1382): lake's service connectors cannot
  yet pull results past the 10,000-row cap.

## Where it has run

**Not on a cluster.** By Steve's decision, this release skips the dev-environment run. The image
(`oramasearch/lake-duckdb:0.2.0@sha256:53e41b38280b91d48c0bcce02b62fcba4f1e7cc9f6ad980f42f7ac812cac4ffb`,
also `v0.2.0` and `main-fe868096`) was built from the tag on the cluster's amd64 BuildKit, with an
SBOM and provenance attestation, and smoke-tested from Docker Hub (linux/amd64 under emulation):
`--version`, a query, a refused `enable_logging` and a refused `COPY` over the database file. The
operator's default image (`lakeServices.duckdbImage`) names `0.1.0` until
[orama-operator#1204](https://github.com/oramasearch/orama-operator/pull/1204) is merged and an
operator release rolls.
